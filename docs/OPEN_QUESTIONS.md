# 未验证的判断与待办实验

这份文件列出我**没来得及验证完**的每一个判断。每条给出：假设、为什么可能成立、

## Q1（最高优先级）学习曲线的后三行

**状态：脚本已写好并在我交付时仍在运行，结果会自己写进 `logs/screening/exp16_capacity.log`。**

已经跑出来的两行（5 折 × 2 重复，主编码世界，CatBoost depth 5，验证折固定不变）：

| 拟合行数 | 占比 | 单模型 OOF | bag |
|---:|---:|---:|---:|
| 4778 | 40% | 0.64927 | 0.65886 |
| 7166 | 60% | 0.66971 | 0.67694 |

还没出来的三行：80%（9555 行）、100%/5 折（11944 行）、100%/**10 折**（13437 行）。

**我的推断：** 从 4778 → 7166（+2388 行）涨了 +0.020，
从 7166 → 11944（+4778 行）根据生产运行的数字应该又涨约 +0.020，
即这个区间里每 1000 行训练数据约值 **+0.004 ~ +0.008 AUC**。
如果成立，说明瓶颈是「每个模型看到多少数据」，不是模型容量。

**怎么看结果：**

```bash
cat logs/screening/exp16_capacity.log
```

**判据：**

- 如果 `10fold_100pct` 的 bag 比 `5fold_100pct` 高 **≥ 0.002** → 立刻把整条流水线换成 10 折
  （`run_oof.py --folds 10`），这是路线图里最便宜的一笔。
- 如果两者差在 ±0.001 内 → 曲线已经在 11944 行附近走平，10 折不值那 80% 的机时，
  跳过 P0 直接做 P1（造编码世界）。
- 如果 `5fold_100pct` 明显低于生产运行里 `cat_d5` 的单种子 OOF（约 0.685–0.690），
  说明这个诊断脚本的种子/抖动流和生产不一致，结论要打折扣（脚本固定用 `stream_offset=1`）。

**如果脚本被中断了，重跑：**

```bash
PYTHONPATH=src2 python3 exp/exp16_capacity.py 2>&1 | tee logs/screening/exp16_capacity.log   # 约 40 分钟
```

**换 10 折之后要注意：** 机时增加 80%，可以把种子数从 12 降到 6–8 换回来。
证据是种子在 8 之后已经饱和（8 → 12 只动了 ±0.0005），而折数还在斜率上。

## Q2 与 B7 `gap` 臂差的那 0.004 到底来自哪

**现象。** B7 报告里 gap 臂 8 种子是 0.69868（旧口径）。减去我实测的早停乐观 +0.00254 后是 0.6962。
但我用诚实协议重跑同一份 gap 特征，4 种子只有 0.69044，外推到 8 种子约 0.692。
**还差约 0.004 没有解释。** 这 0.004 如果能定位，可能是一个可复用的技巧。

三个候选原因，按我认为的可能性排序：

### Q2a 早停让每个模型的树数各不相同，本身给 bagging 增加了多样性

**为什么可能成立。** 他们每折的 best_iter 在 222–762 之间跳，等于每个模型的容量都不一样；
我全部固定 500 棵。集成里成员的"结构多样性"是有价值的，
而这一点**可以在不偷看验证折的前提下复现**。

**怎么验证。** 在 `src2/arms.py` 的 `fit_predict` 里，把 `iterations` 改成从种子决定的随机值：

```python
rng = np.random.default_rng(seed)
n_iter = int(rng.integers(400, 1200))     # 区间要预先定死，不许按分数调
m = CatBoostClassifier(**base, depth=spec["depth"], iterations=n_iter, ...)
```

然后跑 4 个种子对照现有的 4 种子结果：

```bash
PYTHONPATH=src2 python3 src2/run_oof.py --arms cat_d5 --seeds 20260 20261 20262 20263 --stream-base 0 --out artifacts/q2a
```

**判据。** `cat_d5` 的 4 种子 bagged OOF 对比 `artifacts/v2a` 里的 0.69355。
高出 ≥ 0.002 就说明这个机制真实存在，值得推广到所有臂。

### Q2b 他们按概率平均、我按秩平均

**为什么可能成立。** 不同折分区训练出来的模型，概率校准不一样。
秩平均会抹掉"某个模型对某一行特别有把握"的信息，而 `max` 融合恰恰吃这个信息。
在这份数据上 `max` 明显优于平均，说明"把握程度"是有信号的——那么秩平均可能损失了它。

**怎么验证。** 这个我**没有保存逐种子的原始预测**，所以现在无法直接回测，
需要改 `run_oof.py` 让它额外存下每个种子的原始概率：

```python
np.savez_compressed(args.out / f"arm_{name}_perseed.npz",
                    oof=np.array(oof_prob_seeds), test=np.array(test_prob_parts))
```

存下来之后，同一批预测分别按「概率平均」和「秩平均」聚合，比 bagged OOF AUC。

**判据。** 差 ≥ 0.001 就换成更好的那个。这是一行代码的事，值得先做。

### Q2c 单纯是种子数（4 对 8）

**怎么验证。** 把 `run_gap_arm.py` 再跑 4 个种子然后合并：

```bash
python3 src2/run_gap_arm.py --seeds 20294 20295 20296 20297 --out artifacts/v2gap_b
PYTHONPATH=src2 python3 src2/merge_runs.py --inputs artifacts/v2gap artifacts/v2gap_b --out artifacts/v2gap8
```

**判据。** 如果 8 种子的 gap 达到 0.696 附近，那 0.004 就是种子数解释掉的，
Q2a / Q2b 都不用查了。约 19 分钟。

## Q3 最终该交 `views_max` 还是 `views_half`

**现象。** 本地上 `views_max`（0.69910）比加权平均 `views_half`（0.69716）高 0.002，
嵌套选择也 4/5 次选中 `max`。我交的是 `views_max`。

**不确定的地方。** `max` 是一个尾部敏感的算子：它取"最敢下注的那个视图"，
所以单个视图在某些行上的失误会被放大。它在 6398 行的测试子集上的**方差**可能比加权平均大。
本地 OOF 有 14930 行，看不出这个差别。

**怎么验证（不需要提交机会）。** 用 bootstrap 模拟榜单抽样：

```python
# 在 OOF 上重复 1000 次：有放回抽 3199 行（半个测试集大小），分别算两个规则的 AUC
# 比较的不是均值，是 5% 分位数和标准差
```

**判据。** 如果 `max` 的 bootstrap 标准差明显大于 `views_half`（比如大 30% 以上），
而均值只高 0.002，那么在"只有一次提交机会 + 要稳进前三"的目标下，
`views_half` 可能是更好的选择。**这个我没跑，是一个真实的未决问题。**

## Q4 `cat_alt2` 能不能被调强到 0.694 以上

**现象。** 第三个编码世界 `cat_alt2` 与现有臂的相关只有 0.940–0.952（解耦很好），
但单臂 bagged OOF 只有 0.69100，比其它三臂低 0.004，
放进 `max` 反而把 0.69910 拉到 0.69837。

**我的推断（未验证）：** 它弱的原因可能是
① `condition` 按 `region × source` 分组做 z 标准化时，小格子的样本量不够，标准差估计不稳；
② `load = cz - 2.0 * dpc` 里那个系数 2.0 是我随手定的，没调过；
③ 分箱 (4, 9, 16) 偏粗。

**怎么验证。** 分别改这三处，各跑 2 个种子（约 7 分钟/次）：

```bash
PYTHONPATH=src2 python3 src2/run_oof.py --view alt2 --arms cat_alt2 --seeds 20300 20301 --out artifacts/q4
```

**判据。** 单臂 2 种子 bagged OOF 能不能从现在的水平（`artifacts/v2alt2w` 里 4 种子是 0.69100）
提到 0.694 以上。到了就补满 12 种子并加进 `fuse.py` 的 `views_max`。

## Q5 `lgb_te` / `glm` 做强之后的实际价值

**现象。** 这两个臂与主臂的相关只有 0.898 / 0.929，是全场最解耦的，但只有 0.665 / 0.671。

**我的推断（未验证）：** 一个 0.690 且相关 0.90 的臂，在 `max` 融合里的贡献
会超过一个 0.695 且相关 0.955 的臂。**这个"超过"我没有量化过。**

**怎么先验证值不值得投入（不用真的把模型做强）。** 做一个可行性测算：
把现有 `glm` 的 OOF 人为地"变强"——比如按 `0.7*glm_rank + 0.3*cat_d5_rank` 合成一个
AUC 约 0.69、相关约 0.93 的假臂，代入 `fuse.py` 看 `views_max` 会变成多少。

**判据。** 如果假臂能把嵌套 OOF 推到 0.702 以上，就值得认真做 `glm`（分层随机效应 + 张量交互）；
如果只推到 0.700，那还是优先造 CatBoost 编码世界。**这个测算 5 分钟就能做，我没做。**

## Q6 抖动视图的数量在 10 折下是否有不同的最优值

**现象。** 5 折下 `n_views=4` 最好，6 套反而掉 0.002（exp14）。

**我的推断（未验证）：** 那个实验是在 5 折下做的。如果换成 10 折，
每个模型多看 1493 行，能支撑的编码列数量可能不同，`n_views` 的最优值可能上移。

**怎么验证。** 换 10 折之后重扫 `n_views ∈ {3, 4, 6}`。
**判据。** 差异 ≥ 0.002 才算数，否则维持 4。

## Q7 目标编码的贝叶斯化

**现象。** `src2/te.py` 用的是固定平滑系数 `smoothing=30`（`glm` 臂用 50），从没调过，
更没有按列自适应。

**我的推断（未验证）：** 对 `bin_pat`（256 类）、`d5_reg_src`（1000+ 类）这种稀疏交叉，
固定系数肯定不是最优。改成经验贝叶斯——从数据估计每个列的先验方差，
按各自可靠性自适应收缩——应该比固定系数明显更好。

**注意。** 这只影响 `lgb_te` 和 `glm` 两个臂（CatBoost 用的是它自己的有序目标统计量，
不走 `te.py`）。所以这条的价值和 Q5 绑定：只有先确认弱臂值得做，这条才有意义。

**怎么验证。** 先粗扫 `smoothing ∈ {5, 15, 30, 60, 120}`，`lgb_te` 一个种子只要 3 秒。

## Q8 用测试集特征做无标签表示学习（transductive）

**状态：完全没试过。**

测试集的**特征**是给定的，用它做任何不涉及标签的事都不算作弊
（我已经在用：分位切点、车型量纲、频次编码都是在 21328 行全量上拟合的）。没利用的：

- 对类别列做**共现矩阵 + SVD**，给每个 `region` / `source` / `bin_pat` / 交叉格子
  学一个低维稠密向量，再喂给 GBDT；
- 更重的：entity embedding 自编码器，或对比学习（同一行的两个抖动视图互为正样本）。

**为什么可能有用。** 这等于用无标签数据给高基数交叉列学一个先验的相似性结构，
让目标编码不必从零开始估计每个格子——又是在解"目标编码方差"这个核心问题，
和第 2.4 节的机制是同一个主题。

**怎么验证。** 先做 SVD 版本，一小时内能出结论。判据是加进主视图后单臂 OOF 是否 ≥ +0.002。

**风险。** 自监督在 15k 行的表格数据上经常什么都学不到。先做最便宜的版本。

## Q9 天花板到底在哪

**我的估计（推断，不是实测）：** 单模型信息上限约 0.69–0.70，集成上限约 0.705–0.712。

**依据。** 有效特征只有 13 列；主要二阶交互只有 `source × condition` 一个显著项；
单模型无论怎么弄都卡在 0.690 附近。

**这个估计有多可靠：不太可靠。** 它没有考虑我可能漏掉的三阶及以上交互，
也没有考虑 Q8 那类还没试过的方向。**如果谁能把单模型做到 0.695 以上，这个估计就该推翻。**

**一个能真正定界的做法（我没做）：** 用 `days` / `cond_r` / `region` / `source` / `age`
这几列做一个非参数的条件概率估计（比如在细网格上直接算经验概率 + 收缩），
看理论最优排序能到多少。样本量不够可能做不出来，但值得一试。

## Q10 融合规则集的规模与选择方差

**现象。** `fuse.py` 现在有 16 条预登记规则，嵌套选择在 5 个外层块上选中了
`views_max` 4 次、`four_views_max` 1 次。

**不确定的地方。** 16 条规则里做选择本身就有方差。嵌套选择控制住了**报告的**乐观，
但**没有**控制"最终交出去的那条规则是否真的最优"。
如果两条规则的真实水平只差 0.001，嵌套选择基本是在掷硬币。

**怎么验证。** 看 `artifacts/v2/fusion_report.json` 里 `rule_full_oof_auc` 的分布：
`views_max` 0.69910 与第二名 `four_views_max` 0.69875 只差 0.00035，
**这两条在统计上无法区分**。

**建议（我没做）：** 与其在 16 条里选一条，不如把排名靠前的几条**平均**起来交，
这样对选择噪声更稳健。代价是本地数字会略低于最高那条。
